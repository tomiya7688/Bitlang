# Bitlang 開発ワークフロー

## 目的

この文書は、Bitlangプロジェクトで一回の作業を安全に完了するための手順です。作業のたびにリモートの変更を確認して取り込み、既存の作業を保護し、変更をレビュー可能な単位で仕上げます。

## 一回分の作業

一回の作業では、ひとつの目的と完了条件を決め、その範囲を完了してください。複数の独立した目的が見つかった場合は、別の作業として順番に扱ってください。

### 1. 最新状態と作業場所を確認する

1. 通常版BitlangのGitリポジトリ `E:\projects\bitlang\bitlang` に移動してください。
2. `git rev-parse --show-toplevel` でGitルートを確認してください。
3. `git status --short` で未コミット変更を確認してください。自分の作業と既存の作業を見分け、無関係な変更を上書き・削除しないでください。
4. `git fetch origin` でリモートの変更を取得してください。
5. `git status -sb` と `git log --oneline --decorate --left-right HEAD...origin/main` で、現在のブランチと `origin/main` の差を確認してください。

リモートに新しいコミットがある場合は、差分を読み、現在の作業ブランチに取り込んでください。未コミット変更がある場合はその変更を保護し、競合が起きた場合は両方の意図を確認して解決してください。`reset --hard` や作業内容を失う強制操作は使わないでください。リモートに接続できない場合は、その事実と確認できたローカル情報を記録し、取得済みの情報を最新と断定しないでください。

### 2. 作業範囲と完了条件を定める

1. 対象Issueまたは依頼を読み、目的、必要な変更、完了条件を短く書き出してください。
2. [`../../CHANGE_ROUTING.md`](../../CHANGE_ROUTING.md) を使って、対象の仕様、実装、テスト、文書を絞ってください。
3. 仕様が未決定または曖昧な場合は、実装で意味を推測して固定せず、未決定事項を明記してください。
4. 一回の作業で変更するファイルと責務を決めてください。無関係な整理を混ぜないでください。

### 3. 規約に沿って変更する

1. [`../../コーディング規約.md`](../../コーディング規約.md) を確認し、コード、仕様書、設計書、利用者向け説明に適用してください。
2. 手元に [`../../レビュー基準.md`](../../レビュー基準.md) がある場合は、変更の確認に使用してください。このファイルはGitで共有されないため、必須の共有基準はコーディング規約と各言語の規約です。
3. Go実装を変更する場合は [`../../GO_CODING_RULES.md`](../../GO_CODING_RULES.md)、責務索引、[`../../VALIDATION_ROUTING.md`](../../VALIDATION_ROUTING.md) も確認してください。
4. Json-like Comment Outsの宣言コメントは、[日本語仕様](https://github.com/tomiya7688/Json-like-comment-outs/blob/main/docs/jp/SPECIFICATION.md)に従ってください。処理単位の内部コメントは同仕様の範囲に従い、目的・理由・判断を説明してください。
5. Bitlang / Bitlang Explicitの仕様や変換を変更する場合は、データ種類、表現段階、入出力、保持情報、損失情報、拒否条件を明示してください。

### 4. 変更を確かめる

1. 変更した責務に合う検査を [`../../VALIDATION_ROUTING.md`](../../VALIDATION_ROUTING.md) から選び、実行してください。
2. 利用者の実行経路や複数コンポーネントの接続に関わる変更では、該当するE2E検証を実行してください。
3. 実行したコマンドと結果、実行できなかった検査と理由を分けて記録してください。実行していない検査を通過扱いにしないでください。
4. `git diff --check` を実行し、差分に空白エラーがないことを確認してください。

### 5. レビューして作業を閉じる

1. `git diff --` と `git status --short` で変更範囲を確認してください。意図しないファイル、生成物、秘密情報が含まれていないことを確認してください。
2. 規約とレビュー基準に照らし、命名、責務、コメント、潜在的なバグ、安全性、性能、拡張性、文書の読みやすさを確認してください。
3. 目的と完了条件を満たしたか、未完了項目があれば何かを記録してください。
4. 次の作業が残る場合は、独立した一作業として切り出してください。

### 6. Pull Request を作成・レビュー・マージする

1. Pull Requestを作る前に、同じリポジトリの過去のPull Request本文・差分・レビュー・CI結果を確認してください。既存の決定、意図的な延期、検証基準を今回の変更へ反映してください。
2. Pull Request作成前に、基準ブランチとの差分全体をコードレビューしてください。正しさ、安全性、情報損失、責務、命名、性能、テスト不足を確認し、指摘は修正して再検証してください。
3. Pull Requestには目的、変更範囲、過去の関連決定、検証結果、未完了項目を記載してください。未完了または必須検査が失敗している変更はDraftとして扱い、マージ可能と表現しないでください。
4. 最新の基準ブランチとの競合有無と、必須CI・E2E検査の結果を確認してください。未解決のレビュー指摘、失敗・未実行の必須検査、未解決の依存作業があればマージしないでください。
5. コードレビューに未解決の問題がなく、必須検査がすべて成功し、依頼範囲が完了している場合はPull Requestをマージしてください。マージ後にリモート基準ブランチの更新を確認してください。

## 完了報告

各作業の報告には、目的、変更した範囲、実行した検査と結果、未確認項目、リモート取得の成否を記載してください。コミット、プッシュ、Pull Requestの作成などは依頼された場合にだけ実行し、Pull Requestを作成した場合はコードレビューと必須検査を完了するまでマージしないでください。
